## Task 1 — a vault node that is not a regular file never blocks a run

Reproduced on 442a6a9 (exit 124 under `timeout`):
- `.validated-memory/transactions/x.json` a symlink to a FIFO: `init`,
  `journal --check`, `journal --resolve` and `journal --repair` hang.
- a preimage slot that is a symlink to a FIFO: `init` hangs holding the lock.
- `.validated-memory/lock` a dangling symlink: `init` loops forever
  (`lock.py` `_break_if_unowned` opens through the link, gets
  FileNotFoundError, reports "broken", and `continue` skips the deadline).
  A FIFO at `lock` waits the full deadline, then reports busy.

Change:
- A new helper in the journal package, separate from `records.py` (which
  deliberately follows a link to a regular file): `lstat` refuses anything not
  `S_ISREG`, so links are not followed; `os.open(O_RDONLY | O_NONBLOCK |
  O_NOFOLLOW if available)`; `fstat` re-check `S_ISREG`; read.
- `_read_transaction` uses it: a non-regular entry (link, FIFO, directory) is a
  damaged transaction, reason "it is not a regular file; it was not opened".
  The handling of a damaged transaction is unchanged. A regular damaged file
  keeps its 2.5.1 output byte for byte. A transaction entry that is a symlink
  to a valid transaction file becomes damaged: intended, recorded in ADR 0030.
- `mark_*`/`abort`/`remove`/`reestablish` readers in `transactions.py` use it.
- Preimage slot (`_park_preimage` / `_blob_matches`): tested with `lstat`, not
  `exists()` (a dangling link is no longer "absent"). A slot that exists and
  is not a regular file refuses the mutation before any effect, with an ERROR
  that names the slot and says to remove it by hand; the slot is neither
  opened nor removed (the guard treats such a node as residue whose ownership
  is not proven).
- Trusted-preimage restore in `protocol.py`: a non-regular blob is
  "unavailable".
- Lock: `_break_if_unowned` uses `lstat`. A lock path that is not a regular
  file is never opened and never broken; it counts as busy, and the busy ERROR
  names it and says to remove it by hand. The deadline is checked on every
  iteration, so no path loops without bound.

Tests (CLI):
- `transactions/x.json` as {symlink to a FIFO, a FIFO, a directory, symlink to
  a valid transaction file}: `init`, `journal --check`, `journal --resolve`
  (accept, restore, abandon) and `journal --repair` return within the timeout;
  `init` and `--check` exit 1 naming the entry and "not a regular file"; the
  valid-target link is reported damaged, not parsed; the entry is kept.
- A regular `x.json` with garbage: output identical to 2.5.1 ("not valid
  JSON").
- Preimage slot as a symlink to a FIFO while `.gitignore` needs an update: no
  hang, mutation refused, ERROR names the slot and the remedy, slot kept, no
  lock left behind. `journal --resolve --restore` with a FIFO preimage:
  "unavailable".
- `lock` as a dangling symlink and as a FIFO: `init` returns within the lock
  deadline plus margin, exit 1, the ERROR names the lock path.
- Hook with `transactions/x.json` → FIFO: finishes well under 15 s and the
  harness link exists afterwards.

## Task 2 — the session-start run is bounded by the hook

The hook `hooks/restore-memory-symlink.sh` runs `init --harness-memory` under a
15 s hook timeout. `journal/lock.py` waits up to `LOCK_WAIT_SECONDS = 10` for a
live holder, and `init` can acquire twice (`adopting_run`, then
`guarded_harness_repair`): worst case about 20 s, the harness kills the hook.
`adopt.take_over` spends the same budget and no lock flag bounds it.

Change (decided after the Codex SOL challenge; GitLab issue #3 for the new
contract):
- `init --lock-wait SECONDS` (default 10). `init.run` computes one monotonic
  deadline at its start and every lock acquisition of the run shares it
  (`adopting_run`, `guarded_harness_repair`); `Lock` never refreshes it. The
  journal commands keep their own 10 s wait.
- Order kept: each attempt tries to take the lock and breaks a dead or aged
  lock before checking the deadline, so an exhausted budget still recovers a
  breakable lock.
- The hook passes `--lock-wait 3`: a normal sub-second concurrent `init` still
  finishes and relinks; a busy holder withholds within 3 s. The outcome kind is
  unchanged: busy ERROR, exit 1, link withheld with its WARNING.
- Residual, documented and not claimed away: the bound covers lock waiting
  only; `adopt.take_over` can still spend the hook's 15 s.

Tests (CLI, reusing the lock-holding helper in
`tests/test_harness_link_refusal.py`, plus a new helper that writes the pid of
a process that has exited):
- `init --lock-wait 1` against a live holder: elapsed < 3 s, exit 1, the busy message, one run-wide-lock WARNING, link
  unchanged.
- The hook against a live holder: elapsed bounded, link unchanged, the
  WARNING on stderr (the hook always exits 0, so its exit code proves
  nothing).
- Lock breaking under the hook's setting: dead pid → exit 0; empty lock with an
  old mtime → broken; young empty lock → refused within the bound.
- `init` without the setting still waits: `elapsed >= LOCK_DEADLINE - 1` folded
  into the existing test that checks it does not wait twice (no new 10 s
  test).
- The hooks-manifest test pins `--lock-wait 3` in the hook script, and a test
  shows the two acquisitions share one deadline (a holder kept past the first
  acquisition: total elapsed stays under the budget plus margin).

## Task 3 — narrow the outside-process race before the relink

The harness path is inspected in `init.py` before `guarded_harness_repair`
takes the lock; the window is the lock wait plus the vault read. No portable
compare-and-swap on a pathname exists in the standard library, so the race
stays a declared limit, narrowed. Applies to the guarded repair only; the
healthy path already records the expected state in `_record_symlink`.

Change:
- The inspection takes one `lstat` and records `(file type, readlink target if
  a link)`, replacing the separate `is_symlink()` / `readlink()` pair in
  `init.py` (a swap between those two raises an uncaught OSError today). No
  `st_dev`/`st_ino`: another session relinking the same target publishes a
  new inode, and inode numbers are unstable on 9p/drvfs/FUSE. An `lstat`
  failure other than ENOENT is recorded as "could not be read" and the repair
  is withheld.
- One helper, called immediately before `relink()` by both routes that relink
  under the guard (the locked `guarded_harness_repair` and the unlocked
  `_unreadable_repair`), reads the identity again. If the path already
  resolves to the project's `memory/`, nothing is reported (as
  `_link_is_current`). If it changed otherwise, the relink is not made and the
  repair is withheld with the WARNING "the harness path changed while the
  repair waited", without the "; run journal --check" suffix.
- The AST pin in `tests/test_harness_link_refusal.py` is extended: the
  identity check precedes `relink` in the same body.
- The limit is reworded: re-read immediately before the replace; a window of
  one `lstat` and one `rename`, not an atomic guarantee; the relink never
  replaces a directory.

Tests (CLI, using the `before-harness-repair-lock` rendezvous; the unlocked
route through its own rendezvous or an unreadable vault): at the rendezvous
swap the harness path to (a) a regular file with content: content intact,
WARNING "changed", no link; (b) a symlink to elsewhere: that target kept;
(c) the correct link published by someone else: no WARNING, link correct.

## Decision on the lock wait (task 2)

Options: (A) boolean `--no-wait` (every acquisition waits 0); (B)
`--lock-wait SECONDS` with one deadline shared by the run; (C) no flag, the
second acquisition waits 0 and the global wait drops to about 5 s. Chosen: B,
hook value 3 (Codex SOL, 2026-09-30). A withholds the link on every brief
collision between two starting sessions; C exports a hook constraint to every
lock user; a hook-side lock check duplicates the stale-owner logic and races;
a detached retry has no reliable lifecycle, and the next session start is
already the retry.
