# F1 — freshness

Reviewed 2026-09-04 on `feature/review-f1-freshness`, over `derive.py`
(279 LOC), `verdicts.py` (191), `probe.py` (179), `status.py` (252) and
`probes/git_ref.py` (146): 1 047 LOC, 40 % prose. The unit inherits C1's A3
and answers it.

The four design questions went to Codex SOL (`gpt-5.6-sol`, high) before the
central refactor was applied. It approved the shape with a naming correction,
sharpened two of the others, refused the fourth outright — and found a
sentence **written in C1 the same day** to be false. Every claim acted on was
checked by running something.

This is the first unit that made other units smaller: −558 prose bytes in its
own five files, and −436 in `render.py` (V1), −298 in `corpus.py` (M1).

## Axis A — shape

### A1. Three readers of one log, and four places of prose defending the order. Applied (`9010fdb`).

`verdicts` published `records`, `history`, `latest_records` and
`service_view`. Each opened and parsed `verdicts.jsonl` on its own, and only
two of them validated what they returned — `history` handed back whatever
parsed as JSON. Measured, counting `Path.read_text` through a whole run:

    render -> verdicts.jsonl reads: 2

`render.py` called `history()` and `service_view()` on adjacent lines.
`status` avoided the same second read by **reimplementing** `service_view`'s
projection inline:

    view = {key: record["verdict"] for key, record in latest.items()}

And the split had to be defended in four separate places: an eight-line
comment in `render` on why both calls sit together and in which order, nine
lines of `corpus.build`'s docstring saying it again, and a paragraph each in
`history` ("Unlike `service_view`, this does not validate…") and
`latest_records` ("…so the log is still read only once even when both are
wanted"). Prose explaining an ordering constraint is the symptom; the
interface that created the constraint is the defect.

`verdicts.read(root)` reads and validates once and returns a `LogSnapshot`
carrying `records`, `latest` and `view`. There is no order to get right, so
none of that prose has anything left to say.

    derive -> 1 read     status -> 1 read     render -> 1 read

**`LogSnapshot`, not `Log`** — Codex's correction, and it is right: what the
call returns is a validated reading of the file at one moment, not the live
log, and a name that says "log" invites the next reader to expect it to
follow later appends. Its second point is a fair qualification of my own
claim: the public surface does not really go from four names to two, because
the three attributes are part of the interface too. What the unit actually
buys is one read operation with no temporal precondition.

Its refusal is also recorded: pure functions `latest(records)` and
`view(latest)` would have handed the caller back the recipe, the order and
the relations between the projections — less depth, not more.

**What changed in behaviour, and why nothing observable did.** Every record
is now validated whichever projection a caller uses, where `history`
validated none. Measured before the change, on a log holding one record with
an explicit `payload: null`:

    history: 1 records accepted
    service_view: REJECTED -> the 'payload' field is not a mapping

`history`'s only caller called `service_view` in the same breath, so the
refusal already happened in every real run — which is what
`test_a_record_whose_payload_is_null_stops_render_and_writes_nothing` pins,
and it stays green.

### A2. Three names that said the wrong thing. Applied, with A1.

Codex's answer to whether these were worth touching was "yes, but as part of
A1, not as a refactor of their own":

- `_rows(documents)` read the log itself and sat beside a public `rows` — two
  near-identical names in one file, which is what ADR 0011 exists to prevent.
  Its three lines are in `run`.
- `rows(states, view)` is `index_rows`: `status` reusing it justifies the
  function, not the generic name.
- `render_index(rows, basis)`'s first parameter shadowed the module-level
  `rows`. It is `table`.

### A3. C1's inherited question: the configuration read twice in a `probe` run. Closed as accepted (`0361f55`).

Codex's answer was (c), without hedging, and the argument holds:

- Making `Extension` carry the probe registry destroys a semantically useful
  absence — `load` returning `None` means "no extension declared", which
  `contract._check_unit` reads.
- Widening `gated_source` to return the configuration serves one caller and
  forces `derive` to receive something irrelevant to it.
- The saving is a second read of a small file.

So the duplication is accepted and the TODO entry is closed. But it took the
sentence C1 wrote with it: **"this second read can refuse nothing the first
did not" is false.** Two reads are two opens, and nothing holds the tree
still between them — the file can change or vanish in the window. The project
does not promise a snapshot of the working tree, which is why this is not a
reason to redesign anything, and is exactly why it should not have been
asserted as impossible.

## Axis B — prose

### B1. The probe contract was cited where it is not written. Applied (`049bc09`).

`probes/git_ref.py` and `probes/__init__.py` both said the contract is
"documented in the README's `probe` section". **The README has no such
section** — it links to `docs/reference/cli.md#probe`, which is where the
stdin envelope, the stdout answer and the exit-0 rule are written.

Both now cite the document by path, which puts them under a pin that already
exists. Seen red by spelling the fragment `#probing`:

    AssertionError: validated_memory/probes/git_ref.py cites
    'docs/reference/cli.md' with fragment '#probing', but
    'docs/reference/cli.md' has no heading with slug 'probing'

This is the same class of defect C1's B4 records — a documentary reference
of a shape nothing pins — and the reason it is fixed here rather than
deferred is that the honest form of this one *is* pinnable: a path and a
fragment. `probes/__init__.py` belongs to X1; the one-line change there is
this fix's cost outside the unit.

### B2. The incident, told twice, in two modules. Applied (`a2c8d1a`).

`verdicts.anchor_key` carried five lines in the past tense: keyed on
`(system, kind)` alone two anchors collapsed, the later verdict overwrote the
earlier, a `drifted` disappeared behind a `current`, and which one won
depended on the write order. `derive.unit_verdict` repeated the end of it
("no longer collapse into one entry").

Class: **history**. What still binds is one clause, and it belongs where the
key is built — the payload is part of the key because one unit may declare
distinct anchors sharing a `(system, kind)`. Verified pinned, by mutation:
dropping `_canonical(payload)` from the key fails
`test_two_anchors_of_one_system_and_kind_keep_their_own_verdicts` and
`test_the_verdict_of_one_anchor_does_not_move_when_another_is_reprobed`.

`derive` keeps only what it needs as an input contract — `view` is keyed by
`verdicts.anchor_key` — which is Codex's amendment to my proposal to delete
the sentence outright, and it is right: a caller has to know what map it is
handed.

### B3. A restatement where a constraint belonged. Applied (`34e8e96`).

The comment above `_SEVERITY` read "drifted outranks unknown outranks
current" — the mapping on the next line spelled in words, and `worst`'s
docstring says it a third time. Class: **restates the code**, destination 1.

What none of the three said is that the order is *published*:
`docs/reference/cli.md` grades a unit by the worst of its anchors' verdicts,
so reordering the mapping changes what the index and `status` report for
every unit whose anchors disagree. The comment says that now, and the
citation is pinned by `test_docs_links.py`. The behaviour is pinned by
`test_derive_flags_unknowns_alongside_a_worse_drifted_verdict`, which asserts
the cell `drifted (unknown: repo-b)`.

### B4. Claims already pinned, kept.

- **`probe`: "walks the anchors of every *active* unit."** Pinned by
  `tests/test_derive.py::test_only_active_units_are_probed_a_superseded_unit_keeps_its_last_verdict`
  (verified in C1 by measurement: 1 anchor probed across 1 unit on a
  two-unit supersession).
- **`verdicts.NO_PAYLOAD`: a record written before payloads "is never read by
  an anchor".** Pinned by
  `tests/test_render.py::test_a_record_without_a_payload_is_never_attributed_to_an_anchor`
  and `tests/test_derive.py::test_a_record_written_before_payloads_is_never_attributed_to_an_anchor`.
- **`_keyed`: "an unhashable value reaching the dictionary raises `TypeError`
  instead of naming the line at fault."** The same constraint C1 verified in
  `contract._check_supersession_cycles`, here on the log's key fields.

### B5. A false claim removed by A1 rather than corrected.

`records`' docstring said it was "the single place the log is turned into
records, so every reader of it accepts and rejects exactly the same files".
The measurement above shows the two readers built on it did **not** accept
and reject the same files. Under `read` the sentence is true and no longer
needs saying, so it went with the function.

## Rejected, with the reason

- **Splitting `status._check_derived_state`, which takes eight parameters.**
  It is one section of one report, its arguments are the flags the CLI
  parsed, and every candidate cut (a flags object, three functions sharing
  `findings` and `summaries`) moves the same eight values across a new seam
  without removing one. Recorded rather than done, so the next reader knows
  it was looked at.
