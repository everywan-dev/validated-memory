# S1 — the scaffolder

Reviewed 2026-09-04 on `feature/review-s1-scaffolder`, over
`validated_memory/init.py` (1 016 LOC, one public function and fifteen
private ones) and `validated_memory/adopt.py` (220). The unit inherits J4's
A4 and answers it.

The design questions went to Codex SOL (`gpt-5.6-sol`, high) before anything
was applied, and again in a second, narrower round when its first answer
left a coupling unresolved. It refuted one of my five outright, corrected a
second on a point I had measured wrongly, and its correction to a third
turned out to describe a hole in the code rather than in my question. Every
claim of its that was acted on was checked first, by running something.

## Axis A — shape

### A1. The vault's ignore rule is its own vocabulary. Applied.

Five constants and five functions — `IGNORE_FILENAME`, `EXCLUDE_PATH`,
`IGNORE_ENTRY`, `IGNORE_BLOCK`, `IGNORE_EQUIVALENTS`, `_ensure_ignored`,
`_write_entry`, `_carries_entry`, `_read_text`, `_ignore_addition`, about
175 lines — answered one question, "does git ignore the vault, and how do I
make it", inside a module whose docstring says it scaffolds the adopter
layout. `ignore.py` now owns it, on the same argument that took
`install`/`fsync_directory` out of `records.py` in J2.

The cut is the whole behaviour and not only the predicates. Codex's argument
for that is checkable and right: the policy is one algorithm — recognise the
equivalents, try to write, read the executor's refusal, ask
`.git/info/exclude`, error only if both fail — and extracting only
`_carries_entry` and `_ignore_addition` would leave the decision in
`init.py` and produce a module with no depth.

What made that cut non-obvious is `_refusal`. It applies a rule that is
`init`'s and not the journal's — no intention this command forms can be a
no-op, so a `noop` means two readings of one path disagreed — and both the
scaffold and the ignore entry need it. Codex's first answer was to let the
new module read its own outcome, which duplicates that rule (a paragraph of
message, not a line) in two modules; put back to it as a narrow question, it
found the right shape instead: **`write_entry` returns `(reason, outcome)`
and reads neither.** A reason is its own refusal, which is not yet a finding
because the caller asks `ignored_elsewhere` next; an outcome is the
executor's, for `init` to interpret with the rule that is `init`'s. Nothing
in the module prints either, since `init` owns the run's narration.

`init.py`: 1 016 → 859 lines, and the ignore rule is explained once instead
of in both its module docstring and `_ensure_ignored`.

### A2. `_write_entry` returned a reason and read like it returned an error. Applied.

It returns a string on failure and `None` on success, and the string is not
a finding: `_ensure_ignored` asks `.git/info/exclude` next, and a rule there
makes the same failure a non-event. `write_entry`, in the new module, and
its docstring says why the answer is a reason rather than a finding.

### A3. J4's inherited question: should adopting be a step of its own? Recorded.

With `init.py` in front of it, the answer is yes, and Codex's shape for it
is the one worth recording:

```python
with journal.adopting_run(root) as session:   # takes the lock, then reads, then bootstraps
    ...
journal.resolve_transaction(root, transaction_id, resolution)
```

What `init.py` would gain is checkable: it would stop importing and holding
`journal.Lock` itself, stop depending on that lock being re-entrant, and say
in one word that this command adopts. `journal --resolve` would lose the
compensating preflight and the duplicated lookup J4 measured.

Not applied. It changes the journal package's public surface, which is
pinned three ways (`__all__`, `PERMITTED_JOURNAL_EXPORTS`, the layering
test), and it is a decision, not a refactor. **ADR, then TODO.**

### A4. Who owns the concurrency scope. Recorded, with a measurement that changes the question.

Codex's sixth question: `init` takes `journal.Lock` directly because
`adopt.take_over` mutates outside the executor — it copies files, rewrites
`memory/MEMORY.md` and renames the harness directory to `.bak`, none of it
journalled. The comment at the top of `run` says so itself: the lock is
there for "above all the harness take-over in `_sync_symlink`, which moves
an adopter's directory and is not journalled at all".

Chasing that produced the unit's most serious finding, and it is a behaviour
question, not a shape one. **On the journal-failure path the take-over runs
after the lock has been released, and it still absorbs.** Measured on a
scratch tree: adopt it, corrupt `journal.jsonl`, put a real agent-memory
directory at the harness path, run `init --harness-memory`:

```
ERROR: journal.jsonl:14: journal: line is not valid JSON: ...
WARNING: .../harness/memory: journal: the symlink could not be recorded: the
  journal is unavailable (no previous link); restoring it anyway
init: adopted 1 memory file(s) from .../harness/memory
init: parked .../harness/memory -> .../harness/memory.bak
init: created symlink .../harness/memory -> .../adopter/memory
init: 0 created, 0 kept, 1 error(s), 1 warning(s)
```

The adopter's data moved, the project's index was rewritten, the original
was renamed — with nothing able to record any of it, outside the lock the
code says exists for exactly this, and reported as `0 created, 0 kept`.

The other gate does the opposite: with an unignored vault the same directory
is left alone with a WARNING, pinned by
`test_a_gated_run_never_absorbs_the_harness_memory_directory`, whose
docstring gives the reason in general terms — "the adopter's own data moving
after a check that gated" — that applies to both gates equally. `run` passes
`absorb=not unignored`, so only one of the two is refused.

Nothing here is pinned for the journal-failure case, in either direction.
Whether that asymmetry is deliberate is a decision, so this is recorded with
its reproduction rather than fixed, and no test was added: pinning the
current behaviour would entrench the half I am not sure of. **TODO.**

### A5. Five "ensure" functions, five return shapes. Rejected, with the reason.

- `_ensure_dir(path, session)` → `(item, outcome, finding)`
- `_ensure_file(path, content, session)` → the same triple
- `_ensure_views(stdout)` → `(created, kept, findings)`
- `_ensure_ignored(session, stdout)` → findings
- `_sync_symlink(...)` → findings

Codex's answer is that these are three jobs, not one vocabulary: an item, a
batch of up to two items, a global precondition that deliberately counts as
neither, and a fail-open repair. It proposed a shared `ScaffoldResult` for
the first two groups only.

Rejected. `_ensure_dir` and `_ensure_file` produce exactly one item; giving
them a result carrying `created: tuple` and `kept: tuple` to share a type
with the batch widens both signatures to hide a difference that is real.
What the review keeps from the question is A2: the shape that was actually
lying was `_write_entry`'s, and that is fixed.

### A6. `ignore._read_text` and `adopt._read` are the same six lines. Noted, not fixed.

Both mean "a file that cannot be read says nothing", and after A1 they sit
in two modules neither of which may import the other's private name. There
is no third module that is theirs, and inventing one for six lines is worse
than the duplication. It moves with whatever answers A3.

## Axis B — prose

Four incidents out, each already pinned, each replaced by the constraint it
existed to state:

| Where | Sentence | Pinned by |
|---|---|---|
| module docstring | "through 1.5.2 it did exactly that, silently, and handed the file back at 0644" | `test_a_read_only_file_is_refused_and_left_exactly_as_it_was` |
| `_ensure_dir` | "was reported `kept` and journalled as 'directory already present' through 1.5.2" | `test_a_plain_file_where_a_directory_goes_is_refused_not_kept` |
| `_ensure_file` | "used to be reported `kept` and observed as 'file already present'" | `test_a_directory_where_a_scaffold_file_goes_is_refused_not_kept`, `test_a_symlink_to_a_file_where_a_scaffold_file_goes_is_refused_not_kept` |
| `_observe` | "Left to reach `init.run`'s outer handler it became 'the journal could not be opened'" | `test_an_observation_that_cannot_be_recorded_gates_only_its_own_item` |

And two that were not history:

**B1. One incident told twice, five lines apart.** `_refusal`'s docstring
and the comment inside its own `noop` branch both said the function used to
raise `AssertionError`, which `run` does not catch, so the state it exists
to refuse reached the terminal as a traceback. It is told once now, as the
constraint rather than the incident, with the verification argument the
repetition was standing in for: nothing covers this branch, because reaching
it from the CLI seam takes a third party writing between the check and the
execute.

**B2. A shape claim that was not true.** `_ensure_views` said it returns
`(created, kept, findings)` "mirroring `_sync_symlink`'s shape".
`_sync_symlink` returns a list of findings and has no counters. Found
independently by the review and by Codex.

## Two claims about the scaffolder that nothing checked

Both were closed, and the first was seen red.

**`_previous_target` had two answers and one pin.** The pinned one is what a
re-pointing writes; the unpinned one is what every project's first
`--harness-memory` writes — the common case. Without the branch the record
reads `note: "previous target: None"`, a note naming a target that never
existed, and a `link` record's inverse is "restore the previous target".
`test_a_first_link_records_that_there_was_no_previous_target`.

**A test whose name promised more than it checked.**
`test_a_file_that_is_already_identical_is_absorbed_without_a_warning`
asserted exit 0 and the absence of a WARNING, and nothing else. A run that
absorbed nothing at all — never linking the path, never parking the original
— passed under a name saying the file was absorbed. It now asserts the
take-over.
